## Root Cause: `"LLM unavailable"` comes from missing credentials

The error message `"LLM unavailable"` is generated by the [`_fallback()`](backend/analyzer/watsonx_reasoner.py:200) function. It is triggered at **line 269–270** in [`WatsonxReasoner.reason()`](backend/analyzer/watsonx_reasoner.py:269):

```python
if not self._api_key or not self._project_id:
    return _fallback("WATSONX_API_KEY or WATSONX_PROJECT_ID not configured")
```

There are **three possible causes**, in order of likelihood:

---

### 1. ❌ Missing / empty `.env` file (most likely)

[`main.py`](backend/main.py:34) calls `load_dotenv()` which looks for a `.env` file **in the current working directory**, not necessarily in `backend/`. The `.env` file exists at `backend/.env` — so if you start the server from the repo root (`python -m backend.main` or `uvicorn backend.main:app`), `load_dotenv()` may **not find** `backend/.env`.

**Fix — change the load_dotenv call to locate the file explicitly:**

> 🔧 **apply_diff** — backend/main.py

---

### 2. ❌ `.env` file doesn't contain the required keys

Your `backend/.env` must contain **both** of these:

```env
WATSONX_API_KEY=your_iam_api_key_here
WATSONX_PROJECT_ID=your_project_uuid_here
```

Optionally:
```env
WATSONX_URL=https://us-south.ml.cloud.ibm.com
WATSONX_MODEL_ID=ibm-granite/granite-4.0-h-small
```

If either `WATSONX_API_KEY` or `WATSONX_PROJECT_ID` is missing or empty, the check at [`watsonx_reasoner.py:269`](backend/analyzer/watsonx_reasoner.py:269) will immediately return the fallback with `"LLM unavailable"`.

---

### 3. ❌ Other runtime failures (check `llm_error` field)

If credentials are present but the LLM call still fails, the response object also contains a `llm_error` field (from [`ReasoningResult`](backend/analyzer/watsonx_reasoner.py:44)):

```python
llm_error: Optional[str] = None  # set if LLM call or parse failed
```

This field is **not currently included in the `/analyze` response** returned by [`main.py`](backend/main.py:192), so you can't see the actual sub-error in the UI. You'd need to check the server logs where `logger.warning(...)` writes the real exception.

## Root Cause: Wrong `launch.json` — Missing `preLaunchTask`

The root-level [`.vscode/launch.json`](.vscode/launch.json) that VS Code is actually using has **two problems**:

### Problem 1 — No `preLaunchTask`
The root `launch.json` has no `preLaunchTask`, so VS Code launches the extension host immediately without compiling TypeScript first. If `dist/extension.js` is stale or missing, the host process crashes/hangs before JS even runs — causing the **"Extension host did not start in 10 seconds"** message.

The correct config is in [`extension/.vscode/launch.json`](extension/.vscode/launch.json:15) which has `"preLaunchTask": "npm: build"`.

### Problem 2 — Wrong `extensionDevelopmentPath`

However when opened from the repo root, VS Code's task runner resolves `npm: build` relative to the workspace, not the `extension/` subfolder — so the build never runs.
